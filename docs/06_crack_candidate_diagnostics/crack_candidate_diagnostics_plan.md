| `diagnostics/*events.csv`（診断事象） | 作成しない | 現行の生成条件・内容で保存 |

## 目的と優先順位

モデルの想定外の状態が、き裂深さ0・CTSD 0などの結果に紛れて見過ごされないようにする。
最優先は、結果 CSV の対象行から、想定外の有無・種類・発生位置・根拠を確認できることである。
件数の収集や、想定内の終了理由の網羅的な分類を目的にしない。

発端は `B_Smooth_T16_report.json` の 135 MPa における4回分のゼロ履歴である。
ゼロ値だけから異常とは判定しない。また、初期値の履歴が残ったことだけでも異常とは断定しない。
今後の実行で診断を残す計画であり、当時の乱数未固定の結果を遡って確定するものではない。

## 対象範囲

1. 結果 CSV のファイル名・データ行番号から、診断記録を見つけられるようにする。
2. 想定内の判定、想定外の状態、分類未確認を区別する。
3. 想定外の場合は、具体的な状態と発生位置・値を残し、影響を受ける結果との対応を示す。

### 想定内の判定

発生条件不成立、評価対象粒なし、方位による応力条件不成立、進展しきい値未満、
既存最短寿命との比較による計算省略、より短寿命でない候補の非採用は、
想定内であることを確認したうえで、簡潔な状態表示にとどめる。
通常の判定を診断目的だけで例外に変えず、全候補の判定値や件数を網羅的に保存することは必須としない。

### 想定外・適用範囲外の状態

- 必要な補間値を得られない状態（既存の重み関数定義域外など）。数値異常とは区別して記録する。
- 本来有限であるべき計算量の NaN / inf。ただし、既存の破壊表現等で意図的に用いる値は除く。
- 数値計算の前提を満たさない状態。負の寿命積分値や粒層の不足は調査対象とし、
  モデル上の意味を確認してから異常判定条件を確定する。
- 診断状態と採用・出力履歴の矛盾。既存の初期値出力を、それだけで矛盾とはみなさない。

既存の大分類「CTSD評価停止」「寿命積分打ち切り」には通常判定と問題状態が混在し得る。
大分類全体を正常または異常と決めず、実際の分岐と既存資料を確認する。
判断が未確定のものは分類未確認として残し、正常と表示しない。

## 結果行との対応

- 既存 detail CSV のファイル名とデータ行番号（ヘッダーを除く1始まり）をキーとする別の対応表を作る。
- 少なくともき裂深さ0・CTSD 0が同時に出力された各行を対象とする。
- 対応表には、初期履歴か採用履歴か、診断状態、理由の説明、診断記録への参照を含める。
  参照 ID や件数だけを示して理由の推測を求めない。
- 想定外があれば、モデル・応力・繰り返し・要素・対称領域・候補・評価点など、
  発生位置を識別する情報と、既存計算で得た値・しきい値を保存する。
- 候補側の異常が繰り返し全体の結果に影響し得る場合は、該当する候補記録へ対応付ける。
  異常が発生した事実と、その異常がゼロ行の直接原因と確定したことを区別する。
- 想定内の初期値出力には簡潔な理由を示す。診断で確認した範囲を超えて異常なしとは断定しない。
- 全体停止して対象の結果行が存在しない場合も、実行・条件・発生位置を識別して診断を残す。
  存在しない結果行への対応は作らない。

## 例外と実装方針

- 計算前提が成立しない状態は専用の診断例外で明示し、診断を保存できる境界で捕捉する。
- 既存の `CrackLifeDiagnosticError` / `WeightFunctionDomainError` と既存検査を優先して使う。
  想定内の終了は結果の状態として表す。
- 捕捉して記録することと、計算を継続することを分ける。
  既存の `error` は診断保存後に再送出し、`truncate_candidate` の継続範囲は維持する。
  新たな異常の握りつぶし・自動継続・数値補正は追加しない。
- 内部から例外を投げる場合は、コピーされた途中履歴の消失や誤採用を防ぐ。
- 計算核は理由と位置・値を返すか例外に保持し、ファイル保存は出力側で行う。
- 計算式、乱数呼び出し順序、比較・分岐条件、丸め、既存 summary/detail CSV、採用条件を維持する。
  新たな異常検出で停止動作が変わる場合は、対象と変更点を明示して別途検討する。
- 診断用の再計算や乱数呼び出し、グローバル依存、汎用ログ基盤の追加を避ける。
- 既存の `print` を維持し、想定外の状態と診断保存先を標準出力でも確認できるようにする。

### 計算事実と診断表示の分離

初回実装の結果行との対応は維持しつつ、計算側に含まれた診断分類・説明方針を出力側へ移す。
計算側は「何が起きたか」、出力側は「どう分類・説明し、CSVの行へ対応付けるか」を担当する。

| 情報・判断 | 担当 |
| --- | --- |
| 要素・粒・評価点の番号、応力・CTSD・寿命などの値 | 計算側 |
| 履歴の採用有無、採用した粒、初期履歴か計算履歴かという由来 | 計算側 |
| 非有限値、定義域外、粒層不足、負の積分値などの発生事実 | 計算側 |
| `unexpected` / `outside_domain` / `unclassified` という診断表示の分類 | 出力側 |
| 「詳細は保留」「モデル上の意味は未確認」という説明 | 出力側 |
| CSV名、データ行番号、イベントID、列構成、表示用説明文 | 出力側 |

具体的な整理対象:

- `no_candidate_adopted_details_deferred` を、計算事実を表す `no_candidate_adopted` に変更する。
  詳細原因を未分類と表示する判断は出力側で行う。
- `CalculationDiagnostic` は事象の種類と発生位置・値を中心とする記録にする。
  計算側が出力用の `classification` を付与する構造と、例外の `diagnostic()` が
  表示分類を決定する構造を見直し、分類は出力側の小さな対応表で付ける。
- 粒層不足・負の積分値の記録から、`legacy stop retained` / `model meaning unconfirmed`
  などの実装・診断方針を説明する文言を分離する。事象そのものは計算側に残す。
- `history_state` の初期履歴・採用履歴という計算事実と、情報不足時に
  `unclassified` と表示する判断を分ける。ゼロ値から履歴の由来を推測する方式には戻さない。
- 既存例外の技術的なエラーメッセージと構造化された計算位置・値は、単独での調査にも必要なため維持する。
  番号の表示形式や説明の付加は、計算位置という事実と区別して点検する。

有限値条件や補間定義域の検査、例外を投げる判断、途中履歴の保持、既存 policy による停止・継続は
計算動作として維持する。診断表示を分離するために、これらを出力側へ移したり、
専用例外を通常の結果へ一律に置き換えたりしない。

新しい汎用ログ基盤、分類用プラグイン、過剰な型・クラス階層は追加しない。
既存の事象記録と出力側の小さな分類・説明の対応表を使う。
`CalculationDiagnostic` は `reason`・`context`・任意の技術的な `message` のみを保持する。
例外の `diagnostic()` はこの事実記録への変換だけを担当する。
出力側の `_DIAGNOSTIC_DESCRIPTIONS` と `_describe_diagnostic()` が表示分類・説明を付ける。
`history_state` が未提供の場合は計算側で `None` を保持し、出力時に `unclassified` と表示する。
未提供の履歴を採用履歴とみなす説明はしない。
分離作業の進捗・検証は Todo に記録し、初回実装の検証履歴とは区別する。

### 初回実装の出力の参照方法

実行結果フォルダ内の `diagnostics/` に次を保存する。既存の CSV 検証・比較は直下の CSV のみを対象とするため、追加記録は分離する。
従来の `Invoke-ConditionResourcesRun.ps1` の呼び出しのまま出力され、追加オプションは不要。
`--delete-existing-output` では診断 CSV も削除し、前回の異常記録を今回のものと混同しないようにする。

- `<detail CSV名>.rows.csv`: `detail_file` と `data_row` で元 CSV の各データ行を特定する。
  `reason` はその行の説明、`history_state` は `initial` / `adopted` / `unclassified`。
- 同対応表の `observed_classifications` は、その繰り返しで観測した問題の分類。
  `unexpected` は想定外、`outside_domain` は補間の適用範囲外、`unclassified` はモデル上の意味が未確認。
- `<summary CSV名>.events.csv`: 問題が観測された場合のみ作成する。
  対応表の `events_file` / `iteration_event_ids` で参照し、`context` 内の位置・値を確認する。
  `selected_candidate_event_ids` は選択された候補に対応する記録に限定する。
  同じ繰り返しの別候補で発生した問題も残すが、ゼロ行の直接原因とは断定しない。
- `failure.csv`: 全体停止時の例外・context・traceback。停止した荷重条件の結果行は生成しない。

`data_row` と `iteration` は1始まり、要素・順位・対称領域・候補・評価点の `index` は0始まりとする。
全 detail 行に対応表の行を設け、ゼロ行以外からも診断を参照できるようにする。
`no_problem_observed_at_monitored_checks` は検査範囲で問題の記録がないという意味であり、全計算の正常性を保証しない。
採用履歴内のゼロ値の詳細原因は、未確認のまま正常と表示しない。

発生判定に使う値が非有限の場合は、専用例外で検出・捕捉して想定外として記録する。
通常の計算区間の CTSD と寿命積分値にも同じ観測用検査を適用し、不安定破壊時に意図的に入れる inf は対象外とする。
これは既存の比較動作を変えない観測用の検査であり、既存の致命例外を継続可能に変えるものではない。
負の寿命積分値と粒層不足は `unclassified` とし、元の打ち切り・履歴を維持する。

## 検証と完了条件

- 分離後は、計算側の事象記録に CSV名・行番号・イベントID・表示分類・保留方針が含まれないことを確認する。
- 計算事実の記録と、出力側の分類・説明・結果行への対応を分けて軽量検証する。
  分類変更が計算側の変更を必要としないことと、事象の位置・値が失われないことを確認する。
- 既存の想定外・適用範囲外・分類未確認の区別、未選択候補の記録、初期履歴を候補と誤認しない対応を維持する。
- この整理では従来の summary/detail と診断 CSV の列・意味・参照方法を維持する。
  診断 CSV の事象名は `no_candidate_adopted_details_deferred` から `no_candidate_adopted` への変更を明示し、
  それ以外の分類・説明・関連付けに意図しない変更がないことを確認する。
- 想定内のゼロ行、人工的な想定外、分類未確認について、結果行から状態と理由を確認する。
- 想定内の判定を誤って例外にせず、想定外を単なるゼロ履歴や通常の非採用として隠さないことを確認する。
- 非選択候補の問題と選択履歴の対応、全体停止時の診断保存も確認する。
- カウンタの一致だけでは完了としない。既存計算履歴・乱数状態の不変性も確認する。
- 検証入口は `scripts/verification/` 以下の `.ps1` とし、Python は `.venv` を使用する。
- 診断検証は `Invoke-CrackCandidateDiagnosticsVerification.ps1` を使う。
  `-BaselineDir` と `-CandidateDir` を併せて指定すると、再計算せず記録済み CSV の許容誤差0の比較も行う。
  full baseline で再計算した候補と、変更前に確認済みの既存 CSV を比較する際にも使う。
- 通常は compileall（`src verification`）、`Invoke-StaticAnalysis.ps1`、
  `Invoke-ParameterConditionVerification.ps1`、`Invoke-SmokeVerification.ps1` を実施する。
- 開発中は既存 baseline による candidate 比較を優先し、引き渡し前は旧実装も再実行する full baseline 比較を行う。
  baseline を実施する作業単位では smoke / legacy mini は省略可能とする。
- `parameters.py`、`paths.py`、`context.py`、`resources/` に触れた場合は `Invoke-ConditionPreflight.ps1` を実施する。
- 重い通常計算を初手にしない。文書のみの変更では実行検証を省略する。
